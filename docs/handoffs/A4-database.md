## Table inventory (16)

`sources`, `collectors`, `collection_runs`, `raw_records`, `products`,
`product_aliases`, `product_observations`, `variants`,
`variant_observations`, `flavours`, `flavour_observations`,
`change_events`, `leaderboard_snapshots`, `leaderboard_entries`,
`incidents`, `heal_sessions`.

Key decisions:

- **Isolation**: every FK resolves inside `pulse`; the test suite enforces
  this by walking each table's foreign keys and asserting the referenced
  table's schema is `"pulse"`. No legacy table is referenced or reused.
- **raw_records**: jsonb `payload` + `page_fingerprint` + `collector_id`.
  Immutable by convention — the doc comment states writers INSERT only and a
  **future retention trigger** will own row lifecycle (not yet created;
  deliberately deferred so retention policy can settle first).
- **product_observations.status**: `text` + CHECK
  (`product_observations_status_ck`) constrained to
  `candidate | trusted | quarantined | rejected | superseded` — same
  text+CHECK pattern as `signup_reservations` in `auth.ts`. Uniqueness per
  source: `(source_id, slug, observed_at)` OR `(source_id,
  page_fingerprint)` as two partial-free unique indexes.
- **products.current_trusted_observation_id**: FK to
  `product_observations.id` (`set null`). The products↔observations cycle is
  broken with drizzle's `AnyPgColumn` lazy-reference annotation.
- **change_events.event_type**: plain `text`, intentionally unchecked — new
  event kinds ship without a migration (documented on the table).
- **leaderboard_snapshots**: append-only/immutable (comment on the table),
  `rebuilt_at` NOT NULL defaulting to now; entries carry `rank`,
  `metric_key`/`metric_value`, `eligible` + `eligibility_flags` jsonb.
- **incidents.status**: text CHECK `open | resolved`; nullable reference to
  `pulse.collection_runs`. **heal_sessions**: collector ref, `prompt`,
  `preview` jsonb, nullable `approved_at`/`approved_by`.

## Migration route: generated SQL, hand-merged snapshot

`bunx drizzle-kit generate` was attempted first but could not run cleanly in
this worktree: (a) with no local `node_modules`, bunx couldn't resolve
`drizzle-orm` from the worktree; (b) pointing drizzle-kit at the real
migration chain triggered interactive "created or renamed?" dialogs that
cannot be answered non-interactively.

Final route — **SQL generated by drizzle-kit 0.31.9 (the pinned version),
snapshot merged programmatically**:

1. Generated the pulse tables into a fresh scratch out-dir (empty diff base →
   no rename prompts), producing canonical `CREATE SCHEMA/TABLE/INDEX`
   statements for `pulse.*` only.
2. Copied that SQL verbatim to `drizzle/0005_pulserank_pulse_schema.sql`.
3. Merged the fresh pulse-only snapshot into a copy of
   `meta/0004_snapshot.json` (disjoint namespaces: public vs pulse; new id,
   `prevId` = 0004's id) → `meta/0005_snapshot.json`; appended journal idx 5.
4. **Verified** by re-running `drizzle-kit generate` against the union of all
   five schema files: "No schema changes, nothing to migrate 😴" — proving
   snapshot + SQL exactly match the declared schema.

The temp configs/scripts used for steps 1–3 were deleted before commit.
Note for future migrations: `schema/index.ts` does not export `commute.ts`
(or now `pulse.ts`) — both are direct-import modules, so any future generate
config must list schema files explicitly (barrel-only configs will emit DROPs
for commute tables).

## Assumptions & risks

- Assumed export names prefixed `pulse*` (e.g. `pulseProducts`) to avoid
  colliding with legacy `core.ts` names (`incidents`, `collectionRuns`) when
  co-imported; SQL object names stay unprefixed inside the `pulse` schema.
- Left `schema/index.ts` untouched (orchestrator-owned shared exports);
  consumers should import from `@/server/db/schema/pulse` directly, matching
  the `commute.ts` precedent. If the barrel should re-export pulse, that's a
  one-line orchestrator change.
- `collection_runs.status`/`trigger` left as unconstrained text (spec silent);
  A7 can tighten with a CHECK later without data risk.
- The retention trigger for `raw_records` is documented, not implemented —
  tracked as follow-up work once retention policy is decided.
